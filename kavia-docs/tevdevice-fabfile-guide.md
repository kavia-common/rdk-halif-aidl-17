# TEVDevice `fabfile.py` Developer Guide

## Overview and purpose

The `10002556%2FTEVDevice/fabfile.py` file is a Fabric (Invoke-based) automation script used to run a repeatable “build-and-test” flow against a remote host that launches a QEMU virtual machine (VM) image, logs into the VM console automatically, runs a test binary inside the VM, and then powers the VM off. It also collects the execution log back to the local machine for review.

In practice, this fabfile is used as a single command entry point (primarily `fab build`) that:
1. SSHes to a remote machine where QEMU and the VM image artifacts exist.
2. Changes into a fixed remote working directory containing the QEMU kernel and disk image.
3. Launches `qemu-system-x86_64` in an interactive mode over the SSH session.
4. Uses Fabric “watchers” to automatically respond to the VM’s console prompts:
   1. Type `root` at the `login:` prompt.
   2. Once a root shell prompt appears, run `/usr/bin/RDKAVBufferTest`, then `sync`, then `poweroff`.
5. Saves the VM console output to a remote file via `tee`.
6. Downloads that remote log file to a timestamped local log file under `10002556%2FTEVDevice/logs/`.
7. Deletes the remote log file and closes the SSH connection.

## Where this lives in the repo

The fabfile is located at:

`10002556%2FTEVDevice/fabfile.py`

The local logs directory is created alongside the fabfile at:

`10002556%2FTEVDevice/logs/`

## Prerequisites

### Local prerequisites (the machine where you run `fab build`)

You need a Python environment with these packages installed (the fabfile imports them):
- `fabric` (Fabric 2.x style API; imports `task` and `Connection`)
- `invoke` (Fabric uses Invoke; imports `Responder`)
- `python-dotenv` (imports `load_dotenv`)

You also need basic OS access to run Python and create files under the repo (to store logs).

### Remote prerequisites (the machine you SSH into)

The remote host (as hard-coded in the fabfile) must provide:
- An SSH service reachable at the configured IP address.
- A user account matching `HOST` (currently `kavia@121.244.192.84`) and password authentication enabled.
- A directory containing the QEMU artifacts at the configured `REMOTE_PATH` (currently `~/qemu/av_image`), including at least:
  - `bzImage` (Linux kernel image passed via `-kernel`)
  - `core-image-vdevice-xfce-vdevice_x86-64-20260108060504.rootfs.ext4` (root filesystem disk image passed via `-drive file=...`)
  - QEMU installed with `qemu-system-x86_64` available in `PATH`

### VM (guest) prerequisites

Inside the guest VM image, the automation assumes:
- A login prompt appears that includes `login:`
- Logging in as user `root` is accepted without a password prompt (or the flow would need another watcher)
- Once logged in, the root shell prompt matches exactly:
  - `root@vdevicex86-64:~#`
- The test binary exists and is executable:
  - `/usr/bin/RDKAVBufferTest`
- The VM can cleanly shutdown with `poweroff`

## Environment variables and `.env` handling

### `.env` loading

At import time, the fabfile calls:

```python
from dotenv import load_dotenv
load_dotenv()
```

This loads environment variables from a `.env` file if present (typically in the current working directory where `fab` is invoked, subject to `python-dotenv`’s default search behavior). The script does not validate that a `.env` file exists; it only validates that the needed variables are available after loading.

### Required environment variable: `SSH_PASSWORD`

The build task requires `SSH_PASSWORD` and will abort early if it is missing or empty:

- If `SSH_PASSWORD` is missing:
  - It prints an error: `ERROR: SSH_PASSWORD variable is missing.`
  - It returns without attempting any SSH connection.

This password is used for Fabric’s `connect_kwargs={"password": ssh_pass}` (password-based SSH authentication).

## Configuration constants

The fabfile sets a small number of hard-coded configuration variables near the top:

- `HOST = "kavia@121.244.192.84"`
  - The SSH destination in `user@host` form.

- `REMOTE_PATH = "~/qemu/av_image"`
  - The remote directory that is treated as the working directory for QEMU launch and remote log collection.
  - Note: because SFTP does not expand `~`, the script later resolves this to an absolute path before downloading logs.

- `REMOTE_LOG_FILE = "session_output.log"`
  - The name of the remote log file generated by piping QEMU output through `tee`.

### Local log directory behavior

The script determines the directory containing `fabfile.py`:

```python
CURRENT_DIR = os.path.dirname(os.path.abspath(__file__))
LOCAL_LOG_PATH = os.path.join(CURRENT_DIR, "logs")
os.makedirs(LOCAL_LOG_PATH, exist_ok=True)
```

This means logs are always stored under `10002556%2FTEVDevice/logs/` relative to the fabfile, regardless of the working directory where you run `fab`.

## Fabric/Invoke usage and versions (practical notes)

This fabfile uses:
- `@task` decorator from Fabric (`from fabric import task`)
- `Connection` from Fabric (`from fabric import Connection`)
- `Responder` from Invoke (`from invoke import Responder`)

These APIs correspond to Fabric 2.x+ (Fabric 1.x used a different API surface). The watchers mechanism here is the Fabric 2.x/Invoke style where:
- `Connection.run(..., pty=True, watchers=[...])` runs a remote command with a pseudo-TTY and applies responders to the command’s output stream.

If you are using Fabric 3.x, this code is still typically compatible, but package versions should be validated in your environment if issues arise.

## High-level flow of the `build` task

The only defined Fabric task in this fabfile is:

```python
@task
def build(c):
    ...
```

### Step-by-step build flow

#### 1) Validate required environment

The task reads and trims `SSH_PASSWORD`:

```python
ssh_pass = os.environ.get("SSH_PASSWORD", "").strip()
```

If missing or blank, it prints an error and exits.

#### 2) Create an SSH connection

A Fabric `Connection` is created:

```python
conn = Connection(
    HOST,
    connect_kwargs={"password": ssh_pass}
)
```

This uses password authentication. No SSH key handling is configured in this script.

#### 3) Create a timestamped local log filename

A UTC timestamp is generated:

```python
timestamp = datetime.datetime.utcnow().strftime("%Y-%m-%d_%H-%M-%S")
local_log_file = os.path.join(LOCAL_LOG_PATH, f"build_{timestamp}.log")
```

Local logs are written to a unique file per run under `10002556%2FTEVDevice/logs/`:
- Example: `logs/build_2026-01-12_04-27-13.log`

#### 4) Clean old remote log file

Before launching QEMU, the script deletes any previous remote log file:

```python
conn.run(f"cd {REMOTE_PATH} && rm -f {REMOTE_LOG_FILE}")
```

This avoids mixing logs from multiple runs when `tee` appends or reuses the same filename.

#### 5) Launch QEMU and stream output to a file

The fabfile constructs a QEMU command string (see the detailed breakdown below) and runs it from `REMOTE_PATH`, piping combined stdout/stderr to `tee`:

```python
full_command = f"cd {REMOTE_PATH} && ({qemu_cmd_base} 2>&1 | tee {REMOTE_LOG_FILE})"
conn.run(full_command, pty=True, watchers=[auto_login, run_commands])
```

Key implementation detail: `pty=True` is essential here because interactive console automation (responding to prompts) generally requires a pseudo-terminal.

#### 6) Watchers respond to guest prompts and execute tests

Two watchers (Invoke `Responder` instances) are attached:
- One to respond to `login:` with `root\n`
- One to respond to `root@vdevicex86-64:~#` by running the test and shutting down:
  - `/usr/bin/RDKAVBufferTest; sync; poweroff\n`

This makes the full flow “hands-free” as long as prompts match.

#### 7) Download remote log file to local

After QEMU exits (typically because the VM powered off), the script:
1. Sleeps briefly (`time.sleep(2)`) to allow the remote side to flush output.
2. Resolves an absolute path for SFTP:

   ```python
   result = conn.run(f"cd {REMOTE_PATH} && pwd", hide=True)
   absolute_path = result.stdout.strip()
   remote_full_path = f"{absolute_path}/{REMOTE_LOG_FILE}"
   ```

3. Downloads the remote log to the local timestamped file:

   ```python
   conn.get(remote_full_path, local_log_file)
   ```

4. Deletes the remote log:

   ```python
   conn.run(f"cd {REMOTE_PATH} && rm {REMOTE_LOG_FILE}")
   ```

#### 8) Close the SSH connection safely

The `conn.close()` is performed in a `finally:` block, ensuring the connection closes even if something fails mid-run.

## SSH connection and remote execution details

### Authentication

The script uses password-based authentication. Fabric is configured with:

```python
connect_kwargs={"password": ssh_pass}
```

No SSH agent forwarding, key files, or config-file overrides are implemented here.

### Remote command execution model

All actions occur via `Connection.run(...)`, meaning commands run on the remote host, not locally. This includes:
- Removing the old remote log
- Launching QEMU
- Resolving the absolute path of `REMOTE_PATH`
- Removing the remote log after download

File download uses Fabric’s SFTP wrapper via `Connection.get(...)`.

## QEMU command breakdown (flags and meaning)

The QEMU command constructed is:

```text
qemu-system-x86_64 -kernel bzImage
-append "video=1280x720 console=ttyS0 root=/dev/sda"
-drive if=none,id=hd,file=core-image-vdevice-xfce-vdevice_x86-64-20260108060504.rootfs.ext4,format=raw
-device virtio-scsi-pci,id=scsi
-device scsi-hd,drive=hd
-serial mon:stdio
-smp 8 -m 4096
-display vnc=:0
-vga std
-device usb-tablet
-netdev user,id=network0 -device virtio-net,netdev=network0
-usb -device usb-host,vendorid=0x0bb4,productid=0x0a5f
-audiodev id=snd0,driver=none
-device ich9-intel-hda -device hda-duplex,audiodev=snd0
-nic user,ipv6=off,model=e1000,id=network_0,net=10.0.8.0/24,hostfwd=tcp:127.0.0.1:5522-:22
```

### Kernel and boot arguments

- `-kernel bzImage`
  - Boots a Linux kernel image file named `bzImage` from the remote directory.

- `-append "video=1280x720 console=ttyS0 root=/dev/sda"`
  - Passes kernel command line parameters:
    - `video=1280x720` sets a display mode.
    - `console=ttyS0` ensures kernel console is on the first serial port; this is crucial because the script automates login via the serial console stream.
    - `root=/dev/sda` sets the root filesystem device to the first SCSI/SATA disk that appears as `/dev/sda`.

### Disk configuration (root filesystem image)

- `-drive if=none,id=hd,file=<...>.rootfs.ext4,format=raw`
  - Defines a raw disk image file but does not attach it directly to a bus. It is given an ID `hd` to be referenced by a device.

- `-device virtio-scsi-pci,id=scsi`
  - Adds a VirtIO SCSI controller for performance and compatibility.

- `-device scsi-hd,drive=hd`
  - Attaches the previously defined drive (`id=hd`) as a SCSI hard disk.

### Serial console / monitoring

- `-serial mon:stdio`
  - Multiplexes the QEMU monitor and the guest serial console to the process stdio.
  - This is the stream that Fabric “watchers” observe when `pty=True` is enabled and the command is run in the SSH session.

### CPU, memory, display

- `-smp 8`
  - Exposes 8 virtual CPUs to the guest.

- `-m 4096`
  - Allocates 4096 MB RAM to the guest.

- `-display vnc=:0`
  - Exposes a VNC display on display `:0` (port mapping depends on QEMU/VNC conventions; commonly TCP 5900 + display number).

- `-vga std`
  - Uses standard VGA.

- `-device usb-tablet`
  - Provides absolute pointing device input (useful for graphical sessions via VNC).

### Networking

This command configures networking in two ways (both present in the command string):

- `-netdev user,id=network0 -device virtio-net,netdev=network0`
  - Adds user-mode networking with a VirtIO network device.

- `-nic user,ipv6=off,model=e1000,id=network_0,net=10.0.8.0/24,hostfwd=tcp:127.0.0.1:5522-:22`
  - Adds another user-mode NIC using the `e1000` model, disables IPv6, sets a net range, and forwards a host port:
    - `hostfwd=tcp:127.0.0.1:5522-:22` forwards TCP port `5522` on the QEMU host (bound to localhost) to port `22` inside the guest.

Having both `-netdev ...` and `-nic ...` means the guest may see multiple NICs. If this is unintentional, it can complicate networking inside the guest. If it is intentional, document which interface is expected for which use (the current fabfile does not use guest networking directly).

### USB passthrough

- `-usb -device usb-host,vendorid=0x0bb4,productid=0x0a5f`
  - Enables USB and passes through a host USB device identified by vendor/product IDs.
  - This will fail if the device is not present on the remote host or permissions are insufficient.

### Audio configuration

- `-audiodev id=snd0,driver=none`
  - Configures an audio backend with “none” driver (often meaning “no audio output”).

- `-device ich9-intel-hda -device hda-duplex,audiodev=snd0`
  - Adds Intel HDA audio controller and a duplex codec device attached to the `snd0` audio backend.

## Watchers / `Responder` logic (automation details)

### `auto_login` responder

```python
auto_login = Responder(
    pattern=r"login:",
    response="root\n",
)
```

This matches the literal string `login:` in the streamed console output, and responds by typing `root` followed by newline.

If the guest requires a password prompt (for example `Password:`) then this responder alone is insufficient and the flow will hang waiting for manual input or timing out.

### `run_commands` responder

```python
run_commands = Responder(
    pattern=r"root@vdevicex86-64:~#",
    response="/usr/bin/RDKAVBufferTest; sync; poweroff\n",
)
```

Once the root shell prompt appears exactly as `root@vdevicex86-64:~#`, this responder injects a chained command line:
1. Runs the test: `/usr/bin/RDKAVBufferTest`
2. Flushes filesystem buffers: `sync`
3. Powers off the VM: `poweroff`

This design is intentionally simple: it treats the root prompt as “the VM is ready.”

#### Prompt matching sensitivity

The prompt match is exact and depends on:
- The hostname being `vdevicex86-64`
- The prompt formatting matching that string

If the guest image changes its hostname or shell prompt (PS1), the responder may never trigger. In that case, the QEMU session may remain running indefinitely until manually terminated.

## Troubleshooting common issues

### `SSH_PASSWORD variable is missing`

Symptoms:
- The task prints `ERROR: SSH_PASSWORD variable is missing.`
- Nothing else happens.

Fix:
- Export `SSH_PASSWORD` in your environment, or add it to a `.env` file that is loaded by `python-dotenv`.

### SSH authentication failures

Symptoms:
- Connection errors, permission denied, or repeated auth prompts.

Fix:
- Confirm `HOST` is reachable.
- Confirm the username/password are correct.
- Ensure the remote SSH server allows password authentication.
- Consider switching to SSH keys as an improvement (see Security notes and Extension points).

### `REMOTE_PATH` does not exist or is wrong

Symptoms:
- Errors like `cd: ...: No such file or directory`
- `bzImage` not found
- disk image file not found

Fix:
- Verify the remote directory exists and contains:
  - `bzImage`
  - the `.rootfs.ext4` file referenced in the QEMU command
- Update `REMOTE_PATH` and/or the QEMU filenames in the fabfile.

### `qemu-system-x86_64: command not found`

Symptoms:
- Remote command fails immediately.

Fix:
- Install QEMU on the remote host and ensure `qemu-system-x86_64` is on `PATH`.

### Missing QEMU dependencies / permissions

Symptoms:
- QEMU fails with errors related to KVM, permissions, VNC, USB passthrough, etc.

Fix:
- For USB passthrough issues, ensure the referenced USB device exists and the SSH user has permission to access it.
- For VNC issues, ensure the remote host allows QEMU to bind the requested display/port.
- Confirm any required QEMU packages or kernel modules are installed on the remote host.

### Watchers never trigger (hangs at login or shell)

Symptoms:
- The command keeps running, but the expected automated steps do not occur.

Likely causes:
- The guest prompt differs:
  - login prompt is not exactly `login:`
  - shell prompt is not exactly `root@vdevicex86-64:~#`
- The guest requires a password for root login.

Fix:
- Inspect the local log output (if any) or run once without watchers (temporarily) to see actual prompts.
- Update `Responder.pattern` strings to match the guest image’s prompts.
- Add additional responders if a password prompt appears.

### Log download failures (`conn.get`)

Symptoms:
- SFTP errors, “No such file”, or permission denied.

Fix:
- Ensure the QEMU command actually ran and `tee` created the file.
- Ensure the remote path resolution step returns the correct absolute directory.
- Confirm the SSH user has read access to `session_output.log`.

## Security notes

This fabfile uses password-based SSH authentication (`SSH_PASSWORD`), which has security implications:
- The password may be exposed if mishandled in shell history, CI logs, or environment dumps.
- `.env` files can be accidentally committed if not excluded.

Recommended improvements if this is used beyond a controlled development environment:
- Use SSH key authentication (and preferably agent forwarding or a specific key file) instead of passwords.
- Store secrets in a secret manager (CI secret store, vault, etc.) rather than plaintext `.env`.
- Limit the remote user’s permissions and scope.
- Avoid hard-coding IPs/hosts; prefer configuration and allow overrides.

## Extension points (adding more tasks or making it more configurable)

The current fabfile defines only one task: `build`. Common extension patterns include:

### Add host/path overrides

You can add optional parameters to the task (Fabric supports task arguments), for example:
- Host override: `fab build --host user@ip`
- Remote path override: `fab build --remote-path /path/to/qemu/artifacts`

This would reduce the need to edit the file for different environments.

### Add tasks for lifecycle management

Potential additional tasks:
- `fab clean-remote`: remove remote logs and temporary artifacts
- `fab run-qemu`: start QEMU without running tests
- `fab fetch-logs`: fetch logs from a previous run without re-running QEMU
- `fab smoke-test`: run a smaller guest command sequence

### Make QEMU artifacts dynamic

The disk image filename is hard-coded:

`core-image-vdevice-xfce-vdevice_x86-64-20260108060504.rootfs.ext4`

You could:
- Parameterize it (pass via env var or task arg)
- Use a “latest” symlink on the remote host
- Discover the newest matching file using a remote `ls -t` command (be careful to document and handle ambiguity)

### Improve watcher robustness

You can make prompt matching less fragile by:
- Matching `login:` with optional whitespace
- Matching root prompt using a more general regex, for example `r"root@.*:~#"` if appropriate
- Adding responders for password prompts if needed

Any such changes should be validated against the exact guest console output.
